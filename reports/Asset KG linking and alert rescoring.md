# Linking lab assets to threat intelligence for rescoring

The research supports a design that splits the work by data type. Build the asset graph as a minimal custom Neo4j property graph, using CyGraph/MulVAL patterns and D3FEND class names, and populate it from Wazuh syscollector, `nmap -sV` and a hand-written `assets.yaml`. Link it to the CTI KG through two bridges: **Software→CPE** for CVEs and **Host→Platform** for ATT&CK techniques that have no CVE. Map Wazuh alerts by **deterministic JSON-field mapping, not NER**. Re-score with standard CVSS v3.1 Environmental math, then add a bounded uplift for threat, blast radius and alert evidence. The research changes four things in `PLAN.md`. First, **distro packages (dpkg/rpm) should not be matched to NVD CPEs at all**. Every serious scanner (Trivy, Grype, Wazuh ≥4.8) routes them to distro advisories, because backports make NVD version ranges over-report. Second, **validating asset→CVE links against Wazuh is circular** unless it is restricted to links the KG computes independently: Windows/macOS applications and nmap-discovered services. That makes a Windows host a validation requirement, not an optional extra. Third, **CVSS threat metrics can only lower a score**, so any promotion of an alert has to come from environmental metrics or from an uplift outside CVSS. Fourth, the evaluation needs a temporal, KEV-based tier that avoids using KEV as both input and label. One fact in the project's own files blocks most of this: **the CTI KG currently holds only CVEs published from 2024 on** (`docs/cti_kg_methods.md` §1, §8). A lab built on deliberately vulnerable software will mostly carry older CVEs, so the full-corpus run listed under PLAN §0 is a prerequisite for stages 3–6, not housekeeping. Published work does not combine Wazuh alerts, an asset KG and a CVE/CWE/CAPEC/ATT&CK KG for attack paths and rescoring. The researchers' searches suggest this is the thesis's contribution, but their searches were limited and did not establish it.

## A minimal custom graph with borrowed vocabulary beats any single ontology

No standard ontology provides a ready-made, Neo4j-friendly host/service/topology schema. The models that can actually be implemented are MITRE CyGraph's property graph (Machine, Domain, Exploit and Vulnerability nodes; `IN`, `ROUTES`, `LAUNCHES`, `VICTIM`, `PREPARES` edges) ([Noel et al. 2015](https://csis.gmu.edu/noel/pubs/2015_IEEE_HST.pdf)) and MulVAL's Datalog facts `hacl`, `networkService`, `vulExists` and `hasAccount` ([Ou et al. 2005](https://static.usenix.org/event/sec05/tech/full_papers/ou/ou_html/index.html)). D3FEND's Digital Artifact Ontology adds defensible class names such as Network Node, Software, User Account, Configuration Resource and Service Dependency ([D3FEND DAO](https://d3fend.mitre.org/dao/)). UCO/CASE gives property names for IPs, interfaces and connections, but it is RDF-heavy and only worth mapping to if RDF export is wanted ([UCO NetworkInterfaceFacet](https://w3id.org/lmodel/uco-observable/NetworkInterfaceFacet)). Nagaty's "Computer Asset Graph" turns out to be a product catalogue: **101,644 CPEs joined to CVEs, plus 54 platform categories, with no hosts, IPs, services or subnets** (local PDF `ref_papers/Construction_of_a_Unified_Knowledge_Graph_for_Cyber_Threat_Intelligence.pdf`, §IV.B.2). The thesis therefore has to add the instance layer that Nagaty leaves out. Edge names are not standardised across the literature: CyGraph uses `IN`/`ROUTES`, Salayma uses `CONNECTS_TO`/`REACHES`/`HAS`, and the Neo4j white paper uses `DEPENDS_UPON`. The thesis should fix its own vocabulary and give the source each term is adapted from. This supports PLAN §2.2's default of "minimal custom with a mapping table".

The few concrete published asset-KG schemas share one linking pattern: **asset → product identity (CPE) → CVE → CWE/CAPEC → ATT&CK**. BRIDG-ICS (Dec 2025) links an ICS asset ontology through CPE to CVE→CWE→CAPEC→ATT&CK. It keeps observed edges (`COMMUNICATES_WITH`) separate from inferred ones (`HAS_POSSIBLE_*`), a provenance discipline worth copying ([BRIDG-ICS](https://arxiv.org/html/2512.12112v1)). Salayma's IoT attack-graph work is the most reusable Neo4j recipe for a small lab. It models devices, firewall-rule nodes (`ALLOWS`/`DENIES`), a materialised `REACHES` edge, and `Condition`/`Exploit` nodes chained by vulnerability pre- and post-conditions ([Salayma 2024](https://arxiv.org/pdf/2310.01689)). For this project, only the asset side is new. Everything from CPE onward already exists in the CTI KG (`schema.md`).

This report uses PLAN §2.2's own names throughout, so the plan does not need renaming. The asset layer is `Host` {agent_id, hostname, role, zone, cr, ir, ar, criticality}, `OperatingSystem`, `Software` {name, vendor, version, format, arch}, `Service` {proto, port, bind_ip}, `Interface`, `IPAddress`, `Subnet`, `Zone`, `Firewall`, `FirewallRule` {src, dst, proto, dport, action, order}, `UserAccount` and `BusinessFunction`. Its edges are `HAS_INSTALLED`, `RUNS_OS`, `EXPOSES`, `PROVIDED_BY`, `IN_SUBNET`, `DEPENDS_ON`, `SUPPORTS`, `HAS_ACCOUNT_ON`, the derived `CAN_REACH` and `HAS_VULNERABILITY`, and the two bridges `Software-[:MATCHES {method, score}]->CPE` and `OperatingSystem-[:IS_PLATFORM]->Platform`. Every edge carries `source` ('wazuh' | 'nmap' | 'manual' | 'derived') and `updated_at`, so derived edges can be wiped and rebuilt without touching observed facts. One naming detail matters for the Platform bridge. The OS platform string has to be normalised to an existing `Platform.name` (e.g. "Linux", "Windows"), and techniques should be filtered through the KG's `Technique-[:AFFECTS]->Platform` edge rather than by string-matching the raw `x_mitre_platforms` property, because Platform nodes were merged with CWE platform names during alignment (`docs/cti_kg_methods.md` §5). Otherwise every technique-to-host filter can silently return nothing.

### Syscollector covers hosts; topology and value must be authored

Wazuh syscollector covers most of what the outline asks for: OS, hardware, packages, listening and established ports, processes, interfaces, addresses, gateways, users, groups, services and Windows hotfixes. Each category has a server table (`sys_osinfo`, `sys_programs`, `sys_ports`, …) and an indexer index (`wazuh-states-inventory-system-*`, `…-packages-*`, `…-ports-*`, …) ([Wazuh inventory fields](https://documentation.wazuh.com/current/user-manual/capabilities/system-inventory/available-inventory-fields.html)). This confirms PLAN §2.1's choice of syscollector. PLAN names manager REST paths (`/syscollector/{agent}/packages` and so on), but the researchers could not verify them because the API reference page is JS-rendered. The indexer index names are confirmed. Check the API reference for the installed Wazuh version before deciding between the two; the indexer route works either way.

Three gaps need explicit handling. **Wazuh cannot supply MulVAL's `hacl`**, the host-to-host access-control facts that attack paths depend on. Firewall policy, zones, inter-zone flows, asset value, owner and business function must come from a hand-written `assets.yaml`, which is simpler than deploying NetBox for a testbed this size. **Syscollector is host-local**: it misses routers, switches and the attacker node, and it says nothing about what is reachable from where. Running `nmap -sV` from the Kali node and from each zone fills this gap. Its XML gives per-port `service` {product, version, method, conf} and a `cpe` child, plus OS `osclass/cpe` ([Nmap XML output](https://nmap.org/book/output-formats-xml-output.html)), which gives a second, independent CPE route. **Services bound to 127.0.0.1 are not network-reachable.** Filter on the `local_ip` of each syscollector port before creating an `EXPOSES` edge; this is a common error.

### Reachability is a derived edge, evaluated in Python

CyGraph and Salayma both treat reachability as a **materialised, derived relation** that is recomputed whenever topology or rules change. Attack paths are then found with variable-length Cypher or GDS shortest paths ([Noel et al. 2015](https://csis.gmu.edu/noel/pubs/2015_IEEE_HST.pdf); [Salayma 2024](https://arxiv.org/pdf/2310.01689)). PLAN's `(Subnet)-[:CAN_REACH {ports}]->(Subnet)` is too coarse for this. Attack paths need host→service granularity, because MulVAL's logic joins `hacl` with `networkService` on the port. The refinement is to keep zone- or CIDR-level `FirewallRule` nodes (CyGraph's domain abstraction keeps edge counts linear) and derive `(Host)-[:CAN_REACH {proto, port, via_rule}]->(Service)` in Python with first-match, ordered rule evaluation. Do not copy Salayma's `REACHES` query verbatim. Its `WHERE` clause has the form `A OR B OR C AND D`, and because AND binds tighter in Cypher, the firewall check applies only to the multi-hop disjunct (inferred by the researcher from the published query text). The researchers found no 2019–2026 paper with a complete ordered-rule Cypher implementation, so evaluating rules in Python is their recommendation, not a sourced method. The cheap, strong check on this layer is to **compare derived `CAN_REACH` with nmap scans from each zone**. A mismatch means a firewall rule is missing from the model.

### Asset value: never leave CR/IR/AR null

There are four families of asset-value models: per-asset CIA requirement levels (FIPS 199 L/M/H with a high-water mark; CVSS CR/IR/AR), mission tiers from workshops (MITRE Crown Jewels Analysis), dependency-propagated criticality (Jakobson's impact dependency graphs; Neo4j `DEPENDS_UPON*`), and PageRank-style ranking (AssetRank). FIPS 199 defines LOW/MODERATE/HIGH as "limited", "serious" and "severe or catastrophic" adverse effect, and assigns a system the high-water mark across its information types ([NIST FIPS 199](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.199.pdf)). MITRE CJA documents a method (AHP/QFD/FMEA workshops) but no numeric scale ([MITRE CJA](https://www.mitre.org/our-impact/intellectual-property/crown-jewels-analysis)), so it is the right citation for how tiers were assigned rather than for a formula. The workable lab pipeline has four steps. Give each `BusinessFunction` a FIPS 199 triple. Set host `cr`/`ir`/`ar` to the high-water mark over the functions it `SUPPORTS`. Optionally propagate along `DEPENDS_ON`. Keep business value and topological exposure as separate properties.

One schema rule matters more than it looks. **CVSS v3.1 scores "Not Defined" security requirements as Medium (1.0), while CVSS v4.0 scores them as High (worst case)** ([FIRST CVSS v3.1](https://www.first.org/cvss/v3.1/specification-document); [FIRST CVSS v4.0](https://www.first.org/cvss/v4.0/specification-document)). If a host has null CR/IR/AR, the same graph produces different environmental scores depending on which CVSS version is used. PLAN §2.3 should make these three values mandatory.

## Distro packages need vendor feeds; only Windows and nmap need CPE matching

No tool reliably turns a raw dpkg name, Windows DisplayName or banner into the correct NVD vendor:product. The modern scanners avoid trying for OS packages. **Grype disables CPE matching by default for dpkg, rpm and most language ecosystems** (Go, JavaScript, Python, Ruby, Rust, Hex; JVM is an exception) ([Grype configuration](https://oss.anchore.com/docs/reference/grype/configuration/)). Anchore reports that dropping CPEs removed **2,000+ false-positive matches at a cost of 11 false negatives** on its labelled data ([Anchore 2025](https://anchore.com/blog/false-positives-and-false-negatives-in-vulnerability-scanning)). Trivy checks OS packages only against distro advisories (Debian Security Tracker, Ubuntu CVE Tracker, Red Hat OVAL and others) and uses NVD only as a severity fallback ([Trivy docs](https://trivy.dev/docs/latest/scanner/vulnerability/)). The reason is backporting. Distros fix a CVE without changing the upstream version string, so a dpkg version compared against an NVD range over-reports. Trivy's Debian example is CVE-2023-3269: Debian 12's fixed version is `6.1.37-1`, and NVD typically lists only upstream information ([Trivy Debian](https://trivy.dev/docs/v0.67/coverage/os/debian/)). Wazuh itself, since 4.8, correlates syscollector inventory with its own CTI feed. That feed covers Linux distros from vendor feeds and Windows/macOS apps from NVD, normalised to CVE JSON 5 ([Wazuh how it works](https://documentation.wazuh.com/current/user-manual/capabilities/vulnerability-detection/how-it-works.html); [4.8.0 release notes](https://documentation.wazuh.com/4.8/release-notes/release-4-8-0.html)).

This splits the linking pipeline into routes by inventory source:

| Inventory source | Route to CVE | Why |
|---|---|---|
| dpkg/rpm (syscollector) | Wazuh `wazuh-states-vulnerabilities-*`, or Debian/Ubuntu OVAL and trackers | Backports defeat NVD ranges |
| Windows registry programs, macOS apps | Name→CPE matching against the KG, then version-range check in Python | No ecosystem ID exists |
| nmap `-sV` services | nmap's emitted CPE, converted to CPE 2.3 | Independent, network-side evidence |
| pip/npm | purl + OSV/GHSA, not CPE | Ecosystem IDs exist |

For the Windows/nmap route, the most reliable pipeline in the literature is the Vajra recipe. It sanitises names (strips "Inc./LLC", architecture strings, language codes), normalises vendors ("Microsoft Corp." → microsoft), trims versions, generates candidates from a local CPE dictionary in priority tiers, and scores them with RapidFuzz `fuzz.ratio` at ≥70% for the top tier ([Sawant et al. 2024](https://arxiv.org/pdf/2412.16607)). Its evaluation is tiny (7/10 vs 5/10 apps against FleetDM) and measures detection, not precision. CIRCL's cpe-guesser is a fast candidate generator: an inverted index from words to vendor:product pairs, ranked by frequency. But its own README examples return unrelated products, and it outputs no version ([cpe-guesser](https://github.com/vulnerability-lookup/cpe-guesser)). Pair it with a vendor-agreement check and a version-existence check. Dependency-Track adds one cheap guard: it rejects a match when vendor is SUBSET and product is SUPERSET, or the reverse. This stops cases like a `zstandard` CPE matching `pascom_cloud_phone_system` ([Dependency-Track docs](https://docs.dependencytrack.org/analysis-types/known-vulnerabilities/)). PLAN §3.1's sequence of exact match → alias table → RapidFuzz → cpe-guesser → review report is therefore supported, on condition that it is applied only to non-distro software and that the SUBSET/SUPERSET guard is added.

The one head-to-head benchmark shows where the error comes from. In VulCPE's three-system test (a network segment with 4 components, a Linux VM with 46, a Windows VM with 22), **NVD CPE queries reached 0.709 precision and 0.954 coverage, while NVD keyword search reached only 0.149 precision and 0.017 coverage** ([VulCPE](https://arxiv.org/html/2505.13895v1)). Once the CPE is correct, CVE retrieval works. The bottleneck is identifying the CPE. VulCPE's own figure is inconsistent: its prose says 72.6% average precision and its table says 0.766. No peer-reviewed precision/recall exists for cpe-guesser, OpenCVE or embedding/LLM-based inventory→CPE matching. A hand-labelled set of the lab's own few hundred packages would therefore produce a number the literature lacks, which is a small but genuine contribution. The NER work on CPE extraction (CPE-Identifier, F1 95.48%) solves a different problem, CPEs from CVE text, and should not be cited as evidence about inventory matching ([Hu & Thing 2024](https://arxiv.org/html/2405.13568v1)).

### Version ranges belong in Python, and one CTI-KG simplification must be revisited

Neo4j cannot natively order dpkg, rpm or semver versions: string comparison puts "10.0" before "9.0", and Debian `1:2.3-1ubuntu0.4` needs epoch- and revision-aware logic. PLAN §3.2's version check should therefore run in Python with `univers`, which wraps `packaging`, `debian-inspector`, an rpm comparator and semver, and then write the resulting `HAS_VULNERABILITY` edges ([PyPI univers](https://pypi.org/project/univers)). The matcher has to handle two criteria forms in the existing KG. When a CPE node's version is `*`, the bounds are on the `VULNERABLE_TO` edge. When the version is concrete, equality is required, including the `update` field. A version of `-` (NA) is not a wildcard. An alternative is to store a zero-padded integer list as a `version_key` and compare lists in Cypher. That works only for purely numeric versions, and the claim that Cypher compares lists element-wise was **not tested**, because the Neo4j container was not running. Under this design, write `Software-[:MATCHES]->CPE` only to criteria nodes that the installed version actually satisfies, and give `HAS_VULNERABILITY` the properties {via: 'nvd_cpe' | 'wazuh' | 'distro_oval', matched_cpe, matched_range, fixed_version, confidence, computed_at}. That keeps the Host→Software→CPE→Vulnerability chain available as an explanation while giving fast lookups at alert time. A separate `ConcreteCPE` node between Software and the criteria CPE, as one researcher proposed, makes the alignment step more auditable. It is optional.

The linking research surfaced a project-specific risk. `schema.md` states that NVD configurations of the form "application X running on platform Y" (AND nodes) **keep only the vulnerable CPE**. For configuration-dependent CVEs, such as an application flaw that applies only on Windows or a firmware-and-hardware pair, every host running the application will be flagged. Tovarňák et al. and VulCPE address exactly this by evaluating AND/OR configuration graphs ([Tovarňák et al., IM 2021](https://ics.muni.cz/en/research/publications/1786631); [VulCPE](https://arxiv.org/html/2505.13895v1)). The minimal fix is to store the dropped platform CPEs as a `platform_cpes` list on `VULNERABLE_TO` and check them against the host's OS CPE when computing `HAS_VULNERABILITY`. The fuller fix is a `Configuration {operator}` node.

### Validating against Wazuh measures agreement, and is circular for distro packages

PLAN §3 proposes comparing derived `HAS_VULNERABILITY` edges with Wazuh's results. Done naively, this measures Wazuh against itself. If distro-package links come from Wazuh's state index, comparing them back to Wazuh is a tautology. The comparison means something only for links the KG computes independently, that is, the Windows/macOS application and nmap-service partitions. Even there, both sides ultimately depend on NVD, so agreement tests the consistency of CPE matching, not its correctness. The protocol has four steps. Pull `wazuh-states-vulnerabilities-*` through the indexer `_search` API, not from alerts: alerts are not generated on the initial inventory sync, for changes made while the agent was stopped, or for re-evaluations after a feed update ([Wazuh how it works](https://documentation.wazuh.com/current/user-manual/capabilities/vulnerability-detection/how-it-works.html)). Join on (`agent.id`, `package.name`, `package.version`, `vulnerability.id`). Report precision and recall partitioned by `vulnerability.scanner.source` and by OS. Adjudicate a hand-checked sample against NVD and the distro trackers, because Wazuh has its own known false positives, such as Windows MSU gaps. Its `vulnerability.scanner.condition` field ("Package less than X") can be stored on the edge as the human-readable reason for each link. The exact string values of `scanner.source` were not confirmed; inspect one live document. To evaluate the distro route independently, compute links from Ubuntu or Debian OVAL with `oscap oval eval` ([Ubuntu OVAL docs](https://documentation.ubuntu.com/security/security-updates/oval/)). **A practical consequence for PLAN §1 is that the only non-circular validation partition is Windows applications plus nmap services.** A Docker-only lab without a Windows host would lose it, along with most Atomic Red Team coverage.

## Structured alert fields map directly onto the graph, with two traps

Wazuh 4.x alerts need no NLP to reach the KG. `rule.mitre.id`, `rule.mitre.tactic` and `rule.mitre.technique` are arrays (one rule can map to several techniques), and `agent.id`/`agent.name`/`agent.ip` identify the victim host ([Wazuh MITRE docs](https://documentation.wazuh.com/current/user-manual/ruleset/mitre.html)). This confirms PLAN §4.2's rule-based field mapping. Retrieval should go through the indexer's OpenSearch API (`wazuh-alerts-4.x-*`, port 9200) with a `timestamp` range and `search_after` paging ([Wazuh indexer](https://documentation.wazuh.com/4.12/getting-started/components/wazuh-indexer.html)), or be pushed in near real time by an integratord `custom-*` script that receives each alert's file path as `sys.argv[1]` ([Wazuh integrations](https://documentation.wazuh.com/current/user-manual/manager/integration-with-external-apis.html)). This confirms PLAN §4.1. The existing `old_design/wazuh_connector.py` talks to the manager API on port 55000, which does not serve alert history.

The first trap is coverage. By the researcher's own regex count over the v4.14.1 ruleset (168 files), **only 1,015 of 4,515 rules (22.5%) carry a MITRE ID**, using 166 distinct techniques, led by T1484, T1110 and T1078 ([wazuh/wazuh ruleset @ v4.14.1](https://github.com/wazuh/wazuh/tree/v4.14.1/ruleset/rules)). Wazuh publishes no official figure, and the regex did not exclude commented-out rules, so treat the number as approximate. About three-quarters of alerts will therefore have no technique. The fallback is a static `rule.id → technique` lookup, built offline and reviewed by hand. It can use RAM-style LLM prompting over the rule XML ([RAM, arXiv 2502.02337](https://arxiv.org/html/2502.02337v1)) or inheritance from the parent rule (`if_sid`). That makes "rule-based extraction plus an offline LLM back-fill" a defensible answer to PLAN's open question 5. CTI-prose NER models such as CyNER, whose best model reached 76.66% span micro-F1 on CTI text ([CyNER](https://arxiv.org/abs/2204.05754v1)), fit structured SIEM JSON poorly, and no paper evaluating them on Wazuh alerts was found. The second trap is the vulnerability field path. The rules match decoded fields `vulnerability.cve` and `vulnerability.package.name` ([rule 23501–23507](https://github.com/wazuh/wazuh/blob/v4.14.1/ruleset/rules/0520-vulnerability-detector_rules.xml)), and the researcher *infers* that these appear as `data.vulnerability.*` in alert documents. PLAN §4.2 assumes the same path, so check it against one live alert in `alerts.json`. Vulnerability alerts are change events only. Host→CVE state should come from the states index, not from alerts.

### Path queries must be intersected with the host, not enumerated from the CTI side

The closest published blueprint is Sadlek et al. (JISA 2025). They build a kill-chain attack graph with MulVAL rules derived from ATT&CK techniques, match sequences of alerts onto it, and assign severity from the furthest kill-chain phase reached combined with the criticality of the affected assets, reporting **AUC 0.95** for classifying sequences ([Sadlek et al. 2025](https://ics.muni.cz/en/research/publications/2468764)). The researchers did not read its matching algorithm in full. Provenance systems (HOLMES, NoDoze, RapSheet) correlate alerts through OS-level causal graphs ([HOLMES](https://arxiv.org/pdf/1810.01594); [RapSheet](https://www.cs.virginia.edu/~hur7wv/papers/hassan-oakland20.pdf)). The thesis can skip that layer. Replacing MulVAL with Cypher traversal over the linked KG keeps the Sadlek structure and stays within Python + Neo4j. MulVAL is optional, and its CSV output format and import path were not verified.

PLAN §4.3's three query templates are sound. They need three corrections, and any Cypher copied from the research notes needs fixing first. **The notes' example queries use property names that do not exist in this KG** (`t.id`, `v.id`, `v.cvss`, `HAS_CPE`, `RUNS`). `schema.md` keys are `attack_id`, `cve_id`, `cwe_id` and `capec_id`, and CVSS is stored as `cvss3_score`/`cvss4_score`. None of the notes' Cypher has been executed. The first correction concerns fan-out. Technique→CAPEC→CWE→CVE expands to thousands of CVEs, so always intersect it with the alerted host's own `HAS_VULNERABILITY` edges and filter techniques by platform through `AFFECTS`. Normalise sub-techniques as well: link the alert to the exact `attack_id`, and reach the parent through the existing `SUBTECHNIQUE_OF` edge rather than matching both IDs at once, which duplicates rows. Written against the actual schema, the core template is:

```cypher
// Unexecuted; asset-side labels follow PLAN §2.2
MATCH (a:Alert {id:$alert_id})-[:ON_HOST]->(h:Host)-[:RUNS_OS]->(:OperatingSystem)-[:IS_PLATFORM]->(pl:Platform),
      (a)-[:INDICATES]->(t:Technique)-[:AFFECTS]->(pl)
MATCH (t)<-[:USES_TECHNIQUE]-(ap:AttackPattern)<-[:CAUSES_WEAKNESS]-(w:Weakness)
      -[:EXPLOITED_BY]->(v:Vulnerability)<-[:HAS_VULNERABILITY]-(h)
RETURN t.attack_id, ap.capec_id, w.cwe_id, v.cve_id, v.cvss3_score
ORDER BY v.cvss3_score DESC
```

The second correction concerns kill-chain progress: **do not order tactics by their TA IDs**. Reconnaissance (TA0043) and Resource Development (TA0042) come first, and Exfiltration (TA0010) follows Command and Control (TA0011). Store a `Tactic.order` at ingest from the enterprise matrix's `tactic_refs` array. That this array is in matrix order is the researcher's unverified recall, so check it in the STIX bundle already loaded. The third correction concerns tooling. Use Cypher's `SHORTEST k` (which "functionally replaces and extends" `shortestPath()`) for alert-host-to-crown-jewel paths, indexing the lookup properties to avoid exhaustive fallback ([Neo4j shortest paths](https://neo4j.com/docs/cypher-manual/current/patterns/shortest-paths/)). Use `apoc.path.subgraphNodes` with label and relationship filters to compute blast radius ([APOC](https://neo4j.com/docs/apoc/current/overview/apoc.path/apoc.path.subgraphNodes/)), and GDS Personalized PageRank seeded on alerted hosts (`sourceNodes`) to rank affected assets ([GDS PageRank](https://neo4j.com/docs/graph-data-science/current/algorithms/page-rank/)). BloodHound's convention of pointing every edge in the direction of compromise is worth adopting for `CAN_REACH` ([SpecterOps](https://specterops.io/blog/2017/09/18/bloodhound-intro-to-cypher/)). The `Group-[:USES_TECHNIQUE]` overlap with the observed technique set gives a cheap, HOLMES-style "likely next techniques" view.

## A layered score must promote through environment, not threat

The standard frameworks already provide most of a context-aware score, but they have an asymmetry that PLAN §5 needs to account for. **CVSS threat metrics can only lower a score.** In v3.1, E/RL/RC default to 1.0 and every defined value multiplies by ≤1. In v4.0, an undefined Exploit Maturity is scored as Attacked, the worst case ([FIRST CVSS v3.1](https://www.first.org/cvss/v3.1/specification-document); [FIRST CVSS v4.0](https://www.first.org/cvss/v4.0/specification-document)). Threat context inside CVSS can therefore only demote CVEs that are not being exploited. Raising the priority of an alert on a crown-jewel host has to come from environmental metrics (CR/IR/AR = H, MAV = N) or from a term outside CVSS. v3.1's Environmental score is closed-form (`MISS = min(1 − (1−CR·MC)(1−IR·MI)(1−AR·MA), 0.915)`, with CR/IR/AR weights H 1.5, M 1.0, L 0.5). It needs the spec's integer-based Roundup to avoid floating-point errors. v4.0 is not closed-form: it uses a MacroVector lookup with interpolation, so use a maintained library such as RedHat's `cvss` package rather than reimplementing it ([PyPI cvss](https://pypi.org/project/cvss/)). FIRST provides no EPSS→Exploit Maturity mapping, so any mapping is a documented design choice.

On threat signals, EPSS v3 shows why CVSS alone fails as a prioritiser. On the December 2022 test window, **EPSS v3 reached PR-AUC 0.7795 against 0.051 for CVSS v3 base**, and the paper defines efficiency (precision), coverage (recall) and effort ([Jacobs et al. 2023](https://arxiv.org/abs/2302.14172)). EPSS is free through `api.first.org/data/v1/epss`, and the researcher verified live that the `date=` parameter returns historical scores, which is what makes temporal validation possible. The bulk CSV downloaded on 2026-10-17 carries `model_version:v2026.06.15` ([EPSS CSV](https://epss.empiricalsecurity.com/epss_scores-current.csv.gz)). Empirical Security calls this "EPSS v5" ([EPSS v5 post](https://research.empiricalsecurity.com/research/epss-v5-is-here)), but whether FIRST formally designates it as such was **not confirmed**, and the post's reported v4→v5 gain (0.514 → 0.633) is on an unnamed metric. EPSS is not enough on its own: across the KEV catalog, **only 19.9% of CVEs had a peak EPSS ≥ 0.5 before their KEV listing, and 22.4% had no score at all** ([Koscinski et al. 2025](https://arxiv.org/html/2508.13644)). The live KEV feed held 1,748 entries on 2026-10-16 ([CISA KEV](https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json)). The CISA SSVC tree can be computed directly from the KG's stored `ssvc_exploitation`, `ssvc_automatable` and `ssvc_technical_impact` fields plus asset-derived Mission Prevalence and Well-Being, using the exact 36-row Table 9 ([CISA SSVC Guide](https://www.cisa.gov/sites/default/files/publications/cisa-ssvc-guide%20508c.pdf)). The stored values are raw vulnrichment strings (`cti_kg/parse/cve.py::_ssvc` lower-cases only the keys), so normalise them before lookup. The CERT/CC deployer tree, which uses System Exposure, is conceptually the closer fit for a lab that patches its own assets. But the researcher's copy of its outcome table passed through a summarizer, so **verify it row by row against the CERT/CC repository before quoting it** ([CERT/CC deployer tree](https://certcc.github.io/SSVC/howto/deployer_tree/)).

The design that follows from this evidence has seven layers. This is the researchers' synthesis, and no published paper validates it as a whole.

| Layer | Computation | Source of input |
|---|---|---|
| Base `B` | CVSS v3.1 base (and v4 CVSS-B via library) | `Vulnerability.cvss3_*`, `cvss4_*` |
| Environmental `S_env` | Standard v3.1 Environmental: CR/IR/AR from host value; **MAV from KG reachability** (attacker-zone reachable → N, same subnet → A, local → L) | Asset KG |
| Threat in CVSS | E = H/A if in KEV (at evaluation date) or `ssvc_exploitation = active`; P if `poc`; U otherwise | KEV, SSVC fields |
| Threat `T` | EPSS percentile, kept continuous | EPSS API |
| Blast radius `G` ∈ [0,1] | Value of assets reachable *from* the asset once compromised (Personalized PageRank over `CAN_REACH`, or k-hop value sum) | GDS / NetworkX |
| Alert evidence `A` ∈ {0, 0.5, 1} | 1 if an alert on this asset maps to this CVE or a technique linked via CWE/CAPEC; 0.5 if on a neighbour on the path | Wazuh alerts |
| Final | `R = min(10, S_env + (10 − S_env)·(αT + βG + γA)/(α+β+γ))`, plus an SSVC category | — |

The final formula has three useful properties. With no evidence, R equals the standard CVSS-BTE-equivalent score, which is easy to defend in a viva. Demotion happens only through standard metrics. And each context signal closes part of the gap to 10. Keeping MAV (exposure *of* the asset) separate from G (consequences *beyond* the asset) avoids double-counting, and lets an ablation test the two hypotheses separately. PageRank-style values "only indicate relative ranks" ([Sawilla & Ou 2008](https://cse.usf.edu/~xou/publications/esorics08.pdf)), so normalise G rather than treating it as a probability. Set α, β and γ by expert judgement, using AHP as the closest published SOC alert-prioritisation work does, and follow with a sensitivity analysis. That work fuses a TI-KG with an asset-vulnerability graph and scores six AHP-weighted criteria. Its reported 45.2% reduction in response time is self-reported and was seen only as a snippet ([Springer 2026](https://link.springer.com/article/10.1007/s44443-026-01172-w)).

On PLAN's open question 6, the evidence favours **a transparent score as the main contribution, with ML in a supporting role**. Text models reconstruct NVD's *base* metrics, not organisational context: CVSS-BERT reaches 83.79–96.07% per-metric accuracy and MAE 0.73 on the base score ([Shahid & Debar 2021](https://arxiv.org/abs/2111.08510)), and LLMs "often misclassify the same CVEs" ([Jafarikhah et al.](https://arxiv.org/abs/2512.06781)). No public dataset of organisation-specific re-scored CVEs exists to supervise a learned context score. The outline's stage-4 "secBERT" idea therefore fits gap-filling (CVEs missing vectors, v4 back-fill) and alert-text→technique mapping, not the scorer. Nagaty's Phase 4 GNN link prediction fits the same role. Use it as a feature generator, with predicted edges flagged and results reported with and without them, since Nagaty flags "hallucinated" relations as an open problem himself (local PDF, future work). A learned variant (logistic regression or gradient boosting on B, S_env, T, KEV, G, A) is defensible only for the threat component, trained on temporal KEV labels.

## Three evaluation tiers avoid circularity and the unit mismatch

PLAN §6 is directionally right: it uses Atomic Red Team and Kali ground truth, NDCG@k, precision@k, Spearman, and baselines of CVSS, CVSS+environmental, EPSS and SSVC. The research adds two structural problems it has to address. The first is **circularity**: KEV and SSVC exploitation are already features in the KG, so they cannot also serve as labels for the same CVEs. The second is the **unit of analysis**: KEV and EPSS labels are per CVE, while the thesis score is per asset×CVE or per alert. Global labels therefore cannot validate the asset-context layer. The resulting protocol has three tiers.

**Tier A tests the threat layer against global ground truth, per CVE, forward in time.** Freeze inputs as of date T: EPSS via `date=T`, SSVC as of T, and KEV only as known at T. Label CVEs added to KEV in (T, T+30/90 days], and exclude CVEs already in KEV at T. KEV adds few CVEs per month, so use several rolling values of T and longer windows. Report PR-AUC, efficiency/coverage/effort and precision@k, following the EPSS paper's protocol ([Jacobs et al. 2023](https://arxiv.org/abs/2302.14172)). Koscinski et al.'s "score before KEV `dateAdded`" analysis is the citable precedent ([arXiv 2508.13644](https://arxiv.org/html/2508.13644)). Baselines are CVSS-B, CVSS-BT, EPSS alone, KEV-only, the CISA SSVC tree, and the chained rule (KEV ∨ EPSS ≥ 0.088) ∧ CVSS ≥ 7.0, which reported 85.6% coverage with about 95% fewer urgent items ([Shimizu & Hashimoto](https://arxiv.org/abs/2506.01220)). This tier avoids the flaw in Hellsten et al., where KEV fed the very scores it was compared with ([arXiv 2609.37217](https://arxiv.org/html/2609.37217v1)). It also depends on the full-corpus CTI build, since a 2024+ window leaves few labelled positives. The researcher assumed, without verifying, that SSVC values as of T can be recovered from vulnrichment's git history.

**Tier B tests the context layer in the testbed, per asset×CVE and per alert.** Run Invoke-AtomicTest with execution logging. Each record carries technique, test GUID, hostname, IP, user and UTC time ([invoke-atomicredteam wiki](https://github.com/redcanaryco/invoke-atomicredteam/wiki/Execution-Logging)). Script the Kali chains so they log (start, end, step, technique, source IP, target host, CVE). Sync NTP on every VM, then label each alert by host or IP plus a time window, with cleanup and quiet gaps between tests. Inject attack chains against designated crown jewels, mixed with attacks on low-value hosts and benign activity. Grade relevance (e.g. 3 = chain step on a crown jewel, down to 0 = noise) and report NDCG@k, precision@k, MRR and analyst workload to full coverage. Baselines are Wazuh `rule.level`, the linked CVE's CVSS base, CVSS-BT, EPSS, and ablations that remove asset value, reachability, alert evidence and threat in turn. State a tie-break rule explicitly: **CVSS had 198 ties in its top 20** in Koscinski et al.'s data. Expect default Wazuh rules to miss some Atomic tests, which practitioners report ([DEV write-up](https://dev.to/jfash007/deploying-and-validating-a-wazuh-siem-with-atomic-red-team-26i4)). Record "executed, no alert" as a coverage gap rather than a labelling error, and add Sysmon plus `<mitre>`-tagged custom rules. For an external check, **AIT-ADS** fits best: 8 multi-step scenarios and 2,655,821 alerts, 2,293,628 of them from Wazuh, CC BY 4.0. It includes a real CVE (CVE-2020-24186, a wpDiscuz webshell) that allows a CVE→CWE→CAPEC→ATT&CK path test on public data ([Zenodo 8263181](https://zenodo.org/records/8263181)). That CVE is from 2020, so the current 2024+ KG cannot even run this test. Its `labels.csv` gives phase time ranges, not per-alert labels, and the phase→ATT&CK mapping has to be done by hand. No public dataset pairs Atomic Red Team runs with Wazuh alerts, so the lab has to generate its own.

**Tier C measures agreement with experts and the shift relative to CVSS.** Have two or three analysts (the professor, SOC staff) bin a sample of asset×CVE pairs into SSVC-style categories. Report weighted Cohen's κ (or Krippendorff's α) for the new score against the experts, alongside CVSS against the experts. Report Kendall τ / Spearman ρ between the new score and CVSS, but **do not try to maximise it**. A moderate ρ is the expected result for a score that relates to CVSS but reorders it, and a confusion matrix of severity-band changes ("x% of CVSS-High demoted for non-exposed low-value hosts") shows the effect more clearly. Koscinski et al. found κ ≈ 0 between every pair of existing systems, which sets a realistic expectation. Use bootstrap confidence intervals over CVEs or scenarios, a paired permutation test for NDCG, and Benjamini–Hochberg correction when reporting many correlations, as Hellsten et al. do. Two limits should be stated as threats to validity. Tier B and C labels are self-generated, because no public organisation-context ground truth exists. And NDCG is recommended by analogy with information retrieval: none of the prioritisation papers examined reports it. The component checks in PLAN §6.3 (asset→CVE precision/recall, alert→technique accuracy) slot in beneath these tiers, with the asset→CVE check following the partitioned, non-circular protocol above.

## Conclusion

The research shifts where the thesis's difficulty lies. Neo4j queries, attack-path algorithms and scoring formulas are well supplied by prior work. The thesis will succeed or fail at the **identity and truth boundaries**: getting the right CPE for each piece of software, knowing which asset→CVE links are independent enough to validate, and keeping KEV and SSVC from serving as both input and label. Those boundaries are also where the literature is thinnest. No published precision/recall exists for inventory→CPE matching, no paper validates a layered context score against held-out ground truth, and the researchers found no work joining Wazuh alerts to an asset-linked CVE/CWE/CAPEC/ATT&CK KG. The last point should be confirmed with a systematic Google Scholar/arXiv search before it is claimed in writing, because the researchers ran only a few queries. Two leads were seen only as search summaries (arXiv 2603.24888 and 2606.31557).

The most defensible thesis claim is therefore not "a better score than CVSS" but "a standards-anchored score whose every deviation from CVSS can be traced to a graph path and tested by ablation". A measured link-accuracy figure on real lab inventory and a non-circular, temporally honest evaluation give it substance. Two cheap actions should come before any new code. Run the full CVE corpus, since much of the lab's evidence will otherwise be absent from the graph. And fetch one live Wazuh alert and one live states-index document, since several field paths that the alert mapping depends on are still inferred rather than observed.
